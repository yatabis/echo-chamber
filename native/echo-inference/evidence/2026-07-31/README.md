## Retention

## Scope

This evidence set covers the new boundary between the resident Rust/MLX owner
and E.C.H.O.'s TypeScript `ModelPort`:

- Rapid-MLX-compatible production sampling through MLX C;
- protocol-v2 raw-token lineage and revision ownership;
- Qwen XML tool-output parsing;
- tool-result-only continuation through the real Qwen3.6-35B-A3B model;
- the matched native-versus-Rapid-MLX structured-tool comparison, root cause,
  repair, and repeated post-repair gate;
- matched native-versus-Rapid-MLX warm TTFT, total-time, and decode rate;
- a same-time old-binary control and both sequential engine orders for the
  load-time bound-weight fast path;
- a serial-versus-pipelined decode timing decomposition;
- a MoE component breakdown and retained exact decode-score fusion;
- MLX compile/KV-shape checks and rejected decode-graph experiments;
- rejected GDN projection-fusion experiments, including exactness and memory
  tradeoffs;
- cached continuation, existence switching, stateless replay, and resident
  state-memory growth;
- one 6,978-token, nine-revision resident lineage compared with a stateless
  replay of the same final prompt;
- the same nine-step logical tool history through the production native and
  Rapid-MLX session-cache contracts.

The performance conclusions apply only to the retained model, prompt lengths,
sampling, cache modes, warmup, run counts, and machine. They do not establish
concurrent, speculative, other long-context shapes, or next-model-tier
performance, nor broad production-profile structured-tool reliability beyond
the retained exact transport scenario. The long-session cross-engine result is
a production-contract comparison, not a token-identical kernel comparison:
each runtime's adapter-added prompt tokens and state-publication policy remain
load-bearing.

and tensor names, searched those maps, and revalidated static weight
shape/dtype metadata inside every model step. The current runtime resolves the
exact Qwen3.6 layer layout once during model admission, rejects missing or
incompatible static tensors at load time, and retains typed direct MLX array
handles for the execution loop. Dynamic activation and carried-state
validation remains in the request path.

### Decode timing decomposition and the 100 tok/s budget

The runtime now records pure lazy-graph construction separately from
`async_eval` submission/backpressure and sampled-token scalar waits. Two
one-warmup/one-measurement diagnostics used the same 112-token prompt and 128
generated tokens as the retained performance gate.

| Decode measurement                      | Total for 128 | Per token |
| --------------------------------------- | ------------: | --------: |
| Serial: pure graph construction         |      78.58 ms |  0.614 ms |
| Serial: synchronous GPU materialization |   1,560.04 ms | 12.188 ms |
| Serial: complete decode execution       |   1,639.68 ms | 12.810 ms |
| Production: pure graph construction     |      81.35 ms |  0.636 ms |
| Production: `async_eval`/backpressure   |   1,196.07 ms |  9.344 ms |
| Production: sampled-token scalar wait   |     354.64 ms |  2.771 ms |
| Production: complete decode execution   |   1,633.91 ms | 12.765 ms |

The serial run reached 78.08 tok/s and the production split run reached 78.33
tok/s. The serial materialization time demonstrates that the production
`decode_token_wait_nanos` value is only the unhidden tail, not the complete GPU
cost: most GPU work overlaps CPU graph construction and is observed as
`async_eval` backpressure. At 100 tok/s, each independent pipeline producer
must stay below 10 ms/token. Pure graph construction is already below 1 ms,
so it is necessary but not currently limiting; GPU execution at about 12.2
ms/token is the limiting path under this workload.

### QMV specialization and component ablations

MLX 0.32.0 already routes the target decode shapes through its specialized
affine `qmv_fast` and `gather_qmv_fast` Metal kernels. Two custom kernels fixed
the remaining E.C.H.O. conditions at compile time: BF16 input/output, affine
Q4, group size 64, `M=1`, and the admitted Qwen3.6 dimensions. Both reproduced
MLX output exactly for every retained shape.

Graphs were constructed before timing so this comparison isolates evaluation
and submission rather than Python-side custom-kernel configuration:

| Sweep                                 | Nominal weights/scales/biases | MLX median | Custom median | MLX effective rate | Custom effective rate |
| ------------------------------------- | ----------------------------: | ---------: | ------------: | -----------------: | --------------------: |
| 67 distinct dense projections         |                 177,463,296 B |  0.7251 ms |     0.7305 ms |        244.73 GB/s |           242.92 GB/s |
| One layer's 256 experts, gate/up/down |                 452,984,832 B |  1.8577 ms |     1.8494 ms |        243.84 GB/s |           244.93 GB/s |

The dense custom kernel was 0.75% slower; the expert-indexed kernel was 0.45%
faster. The reported effective rates are nominal tensor bytes divided by wall
time, not hardware-counter bandwidth, and omit activations, indices, outputs,
and cache effects. They nevertheless show that replacing MLX's existing
single-matrix QMV is not a plausible source of the roughly 2.4 ms/token that
was still needed for 100 tok/s at this stage. Neither custom QMV was
integrated.

Fixed-length ablations then retained the real 112-token prompt and 128 decode
steps while deliberately bypassing components. Each condition used one warmup
and three measured runs. EOS was ignored to keep the denominator fixed. These
variants produce different, intentionally invalid model outputs, so the
differences are component-cost proxies rather than quality-preserving
optimizations or hardware-profiler attribution.

| ------------------------------------------------- | -------------------------: |
| Common embedding/final norm/LM head/sampling path |                   1.380 ms |
| All 40 MoE blocks                                 |                   5.337 ms |
| All 40 mixer blocks                               |                   5.734 ms |
| Of mixer: 30 GDN blocks                           |                   4.599 ms |
| Of mixer: 10 attention blocks                     |                   1.105 ms |

The first decomposition reconstructs the 12.468 ms/token baseline within
0.017 ms/token. A GDN projection-only proxy, corrected for its one-time lazy
state materialization during finalization, attributes about 1.947 ms/token to
the input normalization, five Q4 projections, and small retained dependency
path, leaving about 2.652 ms/token in GDN-specific convolution, normalization,

That diagnosis selected a decode-shape-specialized GDN surrounding-path fusion

### Retained decode-specialized MoE score fusion

Status update (2026-08-01): this score-only fusion is now a historical
baseline. A later exact stable-selection formulation allowed the complete
post-linear decode route to be fused without changing MLX's BF16 result. See
[`../2026-08-01/README.md`](../2026-08-01/README.md) for the retained
implementation and both-order A/B evidence. The rejection below accurately
describes the earlier prototype, not the current implementation.

Fixed-128-step ablations split the approximately 5.10 ms/token MoE path into
three invalid-output cost proxies: 3.02 ms/token for routed experts, 1.42
ms/token for routing, and 0.89 ms/token for the shared expert. Interaction and
run noise account for the remaining -0.23 ms/token. A controlled four-stage
router run then measured 7.1446 ms/token with MoE removed, 7.7903 with only the
router quantized linear retained, 7.8394 after precise softmax, and 8.3982 for
the complete router dependency. These values make the post-softmax selection
and normalization boundary the largest small-kernel part of the router, but
they remain ablation proxies rather than hardware-profiler attribution.

A complete custom top-k kernel was rejected because BF16 ties changed MLX's
`argpartition` order and could change the selected expert at the cutoff. The
retained implementation therefore leaves precise softmax and `argpartition`
inside MLX. It only fuses the following decode-shape operations: gather eight
selected probabilities, accumulate them in MLX's input-ordered BF16 reduction
order, and normalize the eight scores. Prefill, generic shapes, non-BF16
inputs, and non-normalized top-k retain the original MLX graph.

The fused score path matched all values in 20 random BF16 router cases and one
structured case. The final real-model oracle then reported exact logits,
tokens, all 30 GDN states, and all 10 KV state pairs across a 17-token prefix,
two-token continuation, and two generation steps. The bound resident runtime
also retained exact state, FIFO ordering, cancellation, independent instance
ownership, bad-lineage rejection, and rollback. The prototype and parity
terminal output was synthesized in the local
`qwen36-moe-score-fusion-validation.json`; the raw terminal stream was not
retained, and the durable conclusions are summarized here.

The full model A/B was positive but small and order-sensitive: 12.5431 to
12.5201 ms/token with the old binary first, and 12.6633 to 12.5315 ms/token
with the fused binary first. The router-only isolation was more repeatable:
8.4075 to 8.3387 ms/token in one order and 8.4091 to 8.3349 ms/token in the
reverse order, a 0.069-0.074 ms/token reduction. This is enough to retain the
fusion, but not enough to materially close the remaining 100 tok/s gap.

The final production-contract comparison used one warmup and seven measured
runs per engine in both sequential orders. Native reached 79.68 tok/s versus
Rapid-MLX at 76.36 tok/s with Native first, and 79.66 versus 76.15 tok/s with
Rapid-MLX first. Native was therefore 4.34-4.61% faster in these two blocks;
all 14 greedy output hashes matched and both existing admission gates passed.
The absolute rates were lower than the earlier GDN measurements after a long
diagnostic session, so same-session ratios are more reliable than comparing
absolute values across those sessions. The final binary SHA-256 is
`019961689d8429e1bc46622a57abec4197aefd7f36e87f7d97b91f9a8e8566ac`.

### MLX compile and KV-shape findings

The retained `echo-mlx` tests exercise a compiled dynamic KV update using
`mlx_slice_update_dynamic`, followed by reshape, across capacities 8 and 16
and changed offsets. Outputs remain exact and the compiled closure does not
retrace. A separate compiled SiLU test confirms same-rank dimension changes
reuse one trace while a rank change retraces. This is direct evidence that the
specific dynamic KV-update/reshape pattern is shape-polymorphic on the pinned
MLX 0.32.0 runtime; it is not a blanket guarantee for arbitrary compiled
graphs.

The final validation also exposed a parity-harness-only capacity check that
treated the append/concatenate cache path as a zero-capacity fixed buffer. The
guard now applies only when a fixed-capacity cache is present. The production
buffered path was unaffected, and both full-model and resident-runtime parity
returned to exact 0.0 differences after the repair.

Broader compilation was rejected. The full MoE graph first failed shape
inference around static slice operations; after replacing that operation for
the experiment, it remained exact but fell to 76.48 tok/s. A decode-only
compiled router was exact but reached 76.97 tok/s and increased combined graph
construction/submission time. A compiled router graph also failed when a graph
traced at sequence length 17 was reused at length 2 because a broadcast
retained the traced sequence dimension. These experimental branches were
removed.

### Rejected GDN input-projection fusion

Qwen3.6 GDN layers project the same hidden input through QKV, Z, A, and B
quantized matrices. Three variants tested whether fewer QMM dispatches reduce
the GPU critical path:

- Fusing all four projections for every sequence length was exact at decode
  length 1, but at length 17 direct BF16 maximum differences were 0.015625,
  0.0078125, 0.0078125, and 0.00390625 for QKV, Z, A, and B. The recurrent
  full-model parity amplified this to a 5.625 prefix-state maximum difference
  and was rejected.
- Fusing only A and B preserved exact full-model state. Its 78.686 tok/s
  Native result rose in step with the same run's Rapid-MLX result; the
  Native/Rapid ratio was 99.537%, versus 99.542% for the retained bound-weight
  baseline. There was no measurable normalized gain.
- Keeping the original four weights for prefill but using one fused matrix
  only at decode length 1 preserved exact state and eliminated 90 QMM
  dispatches per generated token. It reached 78.963 tok/s and 99.923% of the
  same-run Rapid-MLX rate, about a 0.4% normalized improvement, but added one
  observed 441,794,860 bytes (421 MiB) of active Metal memory.

The decode-only variant shows that QMM dispatch count is not the dominant
cost: removing 90 dispatches saved only about 0.043 ms/token. Qwen3.6-35B-A3B
has 30 GDN layers, and replacing four projections with one removes three
dispatches in each layer. The memory and complexity cost is especially
unattractive for the planned 122B tier, so all three projection-fusion variants
were removed.

The timing and comparison JSON files are preserved in the ignored local
archive. The direct tensor maximum-difference readings and the rejected
full-state parity failure were observed in diagnostic console output but were
not retained as separate raw artifacts; the values above are therefore
transcribed evidence rather than replayable records.

## Native versus Rapid-MLX long-session contract

The local `qwen36-native-rapid-long-session-performance.json` captured one
warmup and three measured nine-request sessions per engine. Both execute the
same
deterministic tool chain: one initial `advance_probe` call, seven further calls
after padded tool results, and the final exact text
`LONG_SESSION_COMPLETE`. Greedy sampling, BF16 cache state, concurrency one,
the model artifact, and the 825-token growth of every logical revision are
fixed.

This is intentionally not described as token-identical input. Rapid-MLX's
active tool parser injects a 144-token tool-use system suffix, while its
template conversion omits the five-token `strict` field retained by native.
Rapid therefore has a constant 139-token prompt overhead at all nine steps:
its final prompt is 7,113 tokens versus native's 6,974. The retained official
Qwen tokenizer audit and every measured runtime count agree on that
accounting.

The cache contracts also differ by design. Native commits the exact output-end
lineage after every request. Rapid-MLX's
`cache={mode:auto, session_id, session_slot:rolling}` path publishes a
message-boundary checkpoint aligned down to a 2,048-token prefill step while
processing the following request. Consequently, the final request can reuse
the previously published 4,096-token checkpoint; the 6,144-token checkpoint
logged during that request is available only to a later turn.

The comparator does not also send Rapid-MLX's `gdn_state_id`. Source audit
shows that extension snapshots only non-trimmable recurrent layers, excludes
full-attention KV layers, and creates an empty prompt cache only when no other
cache was restored. It is not a complete cached-prefix replacement. Combining
it with the session checkpoint would overwrite the checkpoint's recurrent
layers before the remaining prompt suffix is processed, so it would not
represent native's exact full-state continuation contract.

| Final-request median / count |      Native |   Rapid-MLX | Native / Rapid |
| ---------------------------- | ----------: | ----------: | -------------: |
| Reused prompt tokens         |       6,176 |       4,096 |              — |
| Processed prompt tokens      |         798 |       3,017 |              — |
| Visible TTFT                 | 1,541.64 ms | 4,664.29 ms |         33.05% |
| Total request time           | 1,584.99 ms | 4,734.94 ms |         33.47% |
| Matching final output hashes |         3/3 |         3/3 |              — |

Native is therefore 3.03× faster on visible TTFT and 2.99× faster on total
time in this retained workload. All measured sessions matched the complete
expected native cache trajectory
`0,401,1226,2051,2876,3701,4526,5351,6176` and Rapid trajectory
`0,0,0,0,2048,2048,2048,4096,4096`. All step numbers, prompt growth,
completion counts, and final output hashes matched, and the five-percent
non-regression thresholds passed (`admitted: true`).

## Production structured-tool gate and repair

The local `qwen36-production-tool-format-observations.json` captured three
observations from before the root cause was known:

| Prompt                     | Seed | Stop reason | Valid parsed call |
| -------------------------- | ---: | ----------- | ----------------- |
| Natural tool instruction   |   42 | stop token  | no                |
| Natural tool instruction   |    0 | length 128  | no                |
| Exact XML-envelope request |   42 | stop token  | no                |

The observed text did not contain a valid Qwen XML tool envelope. The parser
correctly preserved it as visible assistant text with a warning instead of
inventing a tool call.

The subsequent matched experiment fixed the same 355-token prompt, tool,
template, maximum output, and 12 seeds. Rapid-MLX returned the correct tool
call in 12/12 attempts with presence penalty 0 and 12/12 with presence penalty
1.5. Native returned 0/12 in both profiles and emitted token ID 0 repeatedly.

First-step instrumentation showed that native and official MLX agreed on
token `248058` (`<tool_call>`) before filtering. Native changed its argmax to
token 0 immediately after top-p. The Rust MLX wrapper was calling
`mlx_cumsum` with `inclusive=false`, while MLX-LM's top-p algorithm requires
an inclusive cumulative probability. If one dominant token alone exceeded the
nucleus cutoff, the exclusive sum caused every candidate to be masked.

A regression that fixes this dominant-token distribution failed before the
repair with sampled token 0 instead of 3. Changing the wrapper to
`inclusive=true` made the regression pass. A release build from the repaired
production source then returned the correct parsed tool call in all 24
attempts:

| Profile      | Native before | Rapid-MLX | Native after |
| ------------ | ------------: | --------: | -----------: |
| presence 0   |        0 / 12 |   12 / 12 |      12 / 12 |
| presence 1.5 |        0 / 12 |   12 / 12 |      12 / 12 |

The exact transport scenario now passes. This removes the evidence for a
tool-turn sampling override or constrained-decoding workaround. Broader prompt
and tool diversity remains a separate production-admission gate.
